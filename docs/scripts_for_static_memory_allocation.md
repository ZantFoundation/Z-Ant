# Scripts for Static Memory Allocation

This document describes 
- how to use `visualise_static_memory_allocation.py` script to generate a Plotly Gantt chart that illustrates the lifetimes of tensors and their buffer usage;
- how to use `compare_static_codegen_flags.py` to compare the static memory allocation plans generated with different heuristic flags (see `docs/heuristics_for_static_memory_planning.md` for more details).

## Visualise Static Memory Allocation

The script `scripts/visualise_static_memory_allocation.py` creates an interactive Gantt chart to visualize how memory is allocated for tensors over time. Each bar in the chart represents a tensor's lifetime, and its color indicates the specific buffer it is allocated to. This visualization is useful for understanding and debugging the static memory allocation of your model.

### How to Use

2. **Run the Script:**

   Once you have the `memory_allocation_<model>.json` file, you can run the Python script to generate the Gantt chart. The script takes the JSON file as a command-line argument.

   First, make sure you have the required Python libraries installed:

   ```sh
   pip install pandas plotly
   ```

   Then, run the script:

   ```sh
   python scripts/visualise_static_memory_allocation.py generated/<model>/memory_allocation_<model>.json
   ```

3. **View the Chart:**

   The script will open a new window or tab in your web browser displaying the interactive Gantt chart. You can hover over the bars to see more details about each tensor, including its size, buffer ID, and lifetime.

### Chart Interpretation

- **Y-axis:** Represents the different tensors in the model.
- **X-axis:** Represents the steps or time.
- **Bars:** Each bar shows the lifetime of a tensor, from when it is borrowed to when it is returned.
- **Colors:** The color of each bar indicates the buffer that the tensor is allocated to. Tensors with the same color share the same buffer.
- **Hover Information:** Hovering over a bar will display detailed information about the tensor, including its name, size, buffer ID, and the duration of its borrow.

## Compare Static Codegen Flags

The script `scripts/compare_static_codegen_flags.py` runs `zig build lib-gen`
for the same model multiple times, once for each explicit static memory
planning ordering:

- `pressure_then_size`
- `pressure_then_liveness`
- `liveness_first`
- `size_first`
- `first_step`
- each of the same flags with `_inverse_first_step` appended

After all runs finish, it writes a local HTML report that compares the memory
plans and build times. This is useful when a model is large enough to use the
heuristic static planner and you want to choose the `-Dstatic_planning` flag
that reserves the least SRAM for that specific graph.

### Why to Use It

Different heuristic orderings can produce different backing-buffer layouts for
the same model. There is no single heuristic that is best for every graph, so
this script is a quick way to test all supported orderings and pick the one
that gives the smallest total static allocation.

This is especially useful when:

- a model is close to the SRAM limit of the target device;
- a new model has just been added and you do not know which static planning
  ordering fits it best;
- a change to the graph, fusion, or memory planner might have affected memory
  usage;
- you want to inspect the generated plans and logs for every planner flag.

For small models this comparison is useless by default. Zant uses the exact
branch-and-bound planner for graphs whose node count is less than or equal to 
`25`. In that case the explicit heuristic flag is not really what decides the
allocation: branch and bound is used, and internally it sorts tensors with the
same ordering as `-Dstatic_planning=enabled` (`size_first`). Therefore the rows
will usually show the same memory result no matter which heuristic flag is used.
Add an extra flag (see below) to force the heuristic planner and compare the
flags on small models as well, if desired.

### How to Use

Run the script from the repository root:

```sh
python scripts/compare_static_codegen_flags.py --model=<model>
```

For example:

```sh
python scripts/compare_static_codegen_flags.py --model=beer
```

By default, the script runs commands equivalent to:

```sh
zig build lib-gen -Dmodel=<model> -Ddynamic=false -Dstatic_planning=<flag>
```

To pass an explicit ONNX path, use `--model-path`:

```sh
python scripts/compare_static_codegen_flags.py --model=<model> --model-path=datasets/models/<model>/<model>.onnx
```

To pass extra Zig build flags, put them after `--`:

```sh
python scripts/compare_static_codegen_flags.py --model=<model> -- -Dbranch_and_bound=0
```

You can also use:

- `--timeout <seconds>` to limit each planner run;
- `--fail-fast` to stop after the first failed run;
- `--no-open` to generate the report without opening it in the browser;
- `--zig <path>` to use a specific Zig executable;
- `--build-arg <arg>` to pass extra `zig build` arguments. This option can be
  repeated.

The main output is:

```text
generated/<model>/static_codegen_planner_comparison.html
```

The script also stores the individual plans and logs in:

```text
generated/<model>/static_planning_comparison/plans/
generated/<model>/static_planning_comparison/logs/
```

### How to Interpret the Results

Open `generated/<model>/static_codegen_planner_comparison.html`. The report
selects the best row automatically by lowest `Static Allocation`, using lowest
build time only as a tie-breaker.

Important columns:

- `Flag`: the `-Dstatic_planning=<flag>` value used for that run.
- `Status`: whether codegen completed successfully. Failed or timed-out runs
  have a log link.
- `Static Allocation`: total memory reserved by all unique backing buffers.
  This is the main value to minimize.
- `Peak Memory Usage`: the estimated maximum live tensor memory at a lifetime
  boundary, using the same calculation as the visualizer.
- `Peak Tensor`: the tensor/lifetime boundary that produced the peak memory
  usage estimate.
- `Overhead`: how much larger the static allocation is than the peak memory
  usage. Lower is better.
- `Buffers`: number of backing buffers emitted by the plan. Fewer buffers is
  often nice, but total allocation matters more.
- `Planner`: whether the run used branch and bound or the heuristic planner.
  If this says `branch and bound`, the heuristic flags are not being compared
  directly.
- `Build Time`: how long that planner run took. Use this as a rough compile-time
  cost, not as the main memory-quality metric.
- `Scale`: visual bar for the row's `Static Allocation`, normalized against
  the largest successful static allocation in the report. A shorter bar means
  that planner reserved less memory than the worst successful run; it is only a
  visual aid, so use the numeric `Static Allocation` value for exact comparison.
- `Files`: links to the copied memory plan and the full build log for that row.

The selected command shown near the top of the report can be copied and reused
as the build command for that model. Usually the best choice is the successful
row with the lowest `Static Allocation`; if two rows reserve the same memory,
prefer the faster or simpler flag.

### Benchmarking Note

Running the script multiple times on the same model will usually make later
runs quicker because generated files and build artifacts may already be warm in
the filesystem and Zig build cache. Use only the first run as a good benchmark
for exact codegen time. Later runs are still useful for checking the memory
result, but they should not be treated as a clean timing measurement.
